# Spec F-002: Oracle scenarios and differential parity harness

## Oracle behavior

This row adds verification infrastructure, not end-user functionality. The behavior authority is the immutable `tui-oracle-baseline` tag at `1cad4ce43cc72d52d4cc4eef920e0da22cb69568`. Captures in `migration/oracle/captures/**` remain checked evidence, not substitutes for the live tagged binary.

1. [S1] A parity scenario is a versioned TOML trace under `migration/oracle/traces/<area>/<name>.toml`; it declares an isolated fixture recipe, terminal dimensions, ordered logical input events, platform support, and expected observations. The parser rejects unknown versions, malformed events, unsupported platform profiles, and missing required fields with a useful diagnostic.
2. [S2] The harness can run a scenario against a TUI executable built from the exact frozen baseline commit in a verified detached worktree, in a per-run temporary fixture and isolated HOME/config/cache roots. It verifies the peeled tag SHA before building and never falls back to the current working tree's `ira` binary.
3. [S3] A standalone `tools/ira-parity` crate exposes UI-neutral `TraceTarget`, `InputEvent`, and `ObservationKind` contracts. `InputEvent` v1 is a strictly ordered tagged enum: `key { code, modifiers, phase }` (phase is press/repeat/release), `text { value }`, `paste { value }`, or `resize { columns, rows }`. Key codes are semantic names (character, Enter, Escape, Tab, Backspace, arrows, Home/End, PageUp/PageDown, Insert/Delete, and F1–F12); modifiers are a set from Shift/Control/Alt/Super. Adapters encode these events for the target while preserving sequence and phase; no Crossterm, GPUI, view, or F-003 action types appear in the schema. The target lifecycle is `start(fixture, dimensions, environment)`, ordered `apply(event)`, `observe(kind)`, and `shutdown()` with exit status. `ObservationKind` v1 is a tagged enum for `process { exit_code, stdout, stderr }`, `terminal_screen`, `domain_snapshot { name }`, `filesystem { relative_path }`, and `persisted_bytes { relative_path }`. Domain snapshot names are feature-owned neutral state labels (such as cwd, ordered panes/entries, cursor, selection, or message), not action IDs. Each target declares its supported observation kinds; a trace may assert only kinds supported by the selected targets, otherwise execution fails with a diagnostic. The TUI PTY adapter implements this contract first; future core or GPUI adapters can consume the same logical events without depending on GPUI view structs or F-003 action names.
4. [S4] The pinned `portable-pty = 0.9.0` backend uses native Unix PTYs on Linux/macOS and ConPTY on Windows. One versioned logical event schema is translated by platform adapters into ordered terminal input bytes/VT events; resize is a first-class event. All live scenarios run on Ubuntu, macOS 14, and Windows MSVC runners; unsupported events are explicit failures, never silent skips. The harness's Windows live-test minimum is Windows 10 version 1809 (ConPTY requirement), independent of IRA's app support policy.
5. [S5] Screen comparison normalizes terminal control sequences and only declared volatile fixture roots while preserving user-visible text, ordering, selection, and messages. Filesystem and persisted-format comparisons remain byte-exact unless a feature spec names a normalized field.
6. [S6] The harness produces actionable diffs naming scenario, observation, expected value, and actual value. Golden-capture mode writes candidate oracle output to a caller-selected staging directory; ordinary test mode never updates approved goldens.
7. [S7] Baseline resolution is fail-closed: fetch the baseline tag if absent, verify peeled SHA `1cad4ce43cc72d52d4cc4eef920e0da22cb69568`, create a detached clean worktree, and build once per test job from that checkout's root manifest and lockfile using the fixed `cargo build --locked --manifest-path <worktree>/Cargo.toml --bin ira` command/profile. The cache key and sidecar contain baseline SHA, OS, target triple, Rust compiler/toolchain, baseline lockfile hash, and fixed build profile; verify all metadata and the executable digest on cache hit. A cache miss builds the exact baseline; a mismatched SHA/digest or failed build is an error. Never use current-HEAD `target/debug/ira` as fallback. Remove the temporary worktree on every exit path, including failed build, cache hit, timeout, and test failure; report cleanup failures alongside the primary failure. Cleanup must close/reap Windows handles before removal. The cached executable is independent of the temporary checkout.
8. [S8] Each scenario runs with a per-scenario deadline; timeout/error terminates the child, waits/reaps with a bounded cleanup deadline, closes PTY handles, drains/joins output readers, and removes the unique fixture. Error output includes both primary and cleanup failures. No sleep-based synchronization; use expected-output readiness/polling with an absolute deadline.
9. [S9] Start child environment from cleared values and set only documented OS-required variables plus isolated roots: Unix `HOME`, XDG config/cache/data, `TMPDIR`, `TERM`, locale; Windows `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `TEMP`/`TMP`, required `SystemRoot`/`WINDIR`, `PATH`, and where needed `HOMEDRIVE`/`HOMEPATH`. Scenario overrides may not redirect any protected HOME, XDG, profile, config, cache, data, or temp root outside that scenario's unique run root. Validate canonicalized paths after applying overrides and fail closed if a protected path escapes; do not follow a scenario-provided symlink to an external location. Ignore no inherited IRA or terminal-host variable. Tests poison parent env and verify fixture/config/temp roots remain isolated.
10. [S10] New/changed golden evidence records the oracle tag/SHA, scenario ID, fixture recipe, dimensions, logical input sequence, OS profile, and capture date. A logic reviewer inspects each committed golden for plausibility; the runner cannot self-approve golden changes.
11. [S11] Tests cover schema validation, fixture isolation, deterministic normalization, a successful tagged-oracle replay on all three native runners, mismatch diagnostics, bounded timeout cleanup, poisoned-env isolation, parallel fixture isolation, and mutation proving an assertion fails when observations differ. No hidden skips or non-`env:` ignores.

## Triggers and surface

No new user-facing `kind:name` surfaces. The harness consumes the versioned abstract input events, fixture metadata, and observation assertions in S1/S3. Platform adapters translate semantic events into target-specific input while preserving exact order, including keys that Crossterm encodes differently by OS.

## State and effects

Per-scenario isolated temporary files only. The runner must clean up fixtures on success and failure, not mutate the user's HOME, app config, oracle tag, committed golden files, or repository root. Golden mode writes to a caller-selected staging directory and never overwrites approved evidence in place.

## Errors and edge cases

- Missing baseline tag, missing oracle executable/build prerequisite, unavailable PTY/terminal driver, malformed trace, timeout, and child failure must have distinct errors with scenario context.
- Timeouts must terminate the child and clean up the per-run fixture.
- Screen normalization must not strip meaningful file names, ordering, selection markers, or messages.
- Parallel scenario runs must use isolated roots and not share terminal sessions or mutable fixtures.
- Tests must not depend on sleeps or network access.

## Config influence and persistence

Each scenario supplies explicit environment overrides and isolated config/cache roots. The harness clears inherited environment before applying the per-OS minimum allowlist in S9; protected profile/config/cache/data/temp roots must remain inside that scenario's unique run root after overrides and path resolution. Never read/write the developer's normal IRA config. Persisted state and filesystem outcomes are compared byte-for-byte where the owning feature spec requires compatibility.

## Platform notes

The oracle is a terminal program while the target is a native desktop app. `portable-pty 0.9.0` is pinned to provide Unix PTYs and Windows ConPTY without an extra runtime tool; the resolved dependency license closure and native Windows replay are verified by F-150. The same live scenarios run on Linux, macOS, and Windows; do not report schema/golden-only checks as live behavior. Windows ConPTY test support requires version 1809 or later; this is not the app's support policy.

## GPUI/desktop surface

No GPUI dependency in the harness and no UI behavior implementation. A future adapter may translate a scenario into core actions/headless GPUI inputs while the TUI adapter remains frozen and separate. The harness must permit native window smoke evidence to be recorded separately from deterministic core comparisons.

## Write-set and dependencies

Write-set: `tools/ira-parity/**` (including its own Cargo manifest, lockfile, and tests), `migration/oracle/traces/**`, and `migration/reports/F-002/**`. Root/desktop manifests and lockfiles, workflow files, `scripts/parity_gate.py`, the matrix, other oracle captures, and TUI source/tag remain untouched. F-150 owns CI workflow integration. Preserve all existing captures.
