# Spec F-002: Oracle scenarios and differential parity harness

Matrix row: F-002 | Inventory: INV-DOCS-002; all nine behavior inventories | Wave: 0 | Deps: F-001
Status: draft for architecture and platform pre-review

## Oracle behavior

This row adds verification infrastructure, not end-user functionality. The behavior authority is the immutable `tui-oracle-baseline` tag at `1cad4ce43cc72d52d4cc4eef920e0da22cb69568`. Captures in `migration/oracle/captures/**` remain checked evidence, not substitutes for the live tagged binary.

1. [S1] A parity scenario is a versioned, deterministic description of an isolated initial fixture, terminal/window dimensions where relevant, ordered input events, and expected observable results. It must reject unknown versions, malformed inputs, and missing required fields with a useful diagnostic.
2. [S2] The harness can run a scenario against the TUI executable built from the frozen baseline, in a per-run temporary fixture and isolated HOME/config/cache roots. It must not accidentally launch the current working tree's `ira` binary as the oracle.
3. [S3] The runner records the declared observations available for that scenario: normalized terminal screen/messages, process exit/stdout/stderr, relevant filesystem tree and bytes, and persisted state. A scenario need not assert every observation, but assertions are explicit and deterministic.
4. [S4] Screen comparison normalizes terminal control sequences and volatile fixture roots while preserving user-visible text, ordering, selection, and messages. Filesystem and persisted-format comparisons remain byte-exact unless a spec clause explicitly names a normalized field.
5. [S5] The harness produces actionable diffs naming scenario, observation, expected value and actual value. It has a golden-capture mode that writes candidate oracle output separately from committed expectations; ordinary test mode never updates goldens.
6. [S6] A trace can be replayed through independent targets so later F-002 consumers can compare a core/desktop adapter with the frozen TUI oracle without embedding GPUI in the harness. The trace schema must not prescribe UI internals or weaken the TUI's ordered input semantics.
7. [S7] New or changed golden evidence records the oracle tag, scenario ID, fixture recipe, dimensions, input event sequence, and capture date. A logic reviewer inspects each committed golden for plausibility; the runner cannot self-approve golden changes.
8. [S8] Tests cover schema validation, fixture isolation, deterministic normalization, a successful tagged-oracle replay, mismatch diagnostics, and a mutation proving an assertion fails when observed output differs. Platform-limited execution is stated explicitly; no hidden skips or non-`env:` ignores.

## Triggers and surface

No new user-facing `kind:name` surfaces. The harness consumes abstract input events, fixture metadata and observation assertions. Event representation is a pre-review question; it must preserve exact ordering and support keys that `crossterm` encodes differently by OS.

## State and effects

Per-scenario isolated temporary files only. The runner must clean up fixtures on success and failure, not mutate the user's HOME, app config, oracle tag, committed golden files, or repository root. Golden mode writes to a caller-selected staging directory and never overwrites approved evidence in place.

## Errors and edge cases

- Missing baseline tag, missing oracle executable/build prerequisite, unavailable PTY/terminal driver, malformed trace, timeout, and child failure must have distinct errors with scenario context.
- Timeouts must terminate the child and clean up the per-run fixture.
- Screen normalization must not strip meaningful file names, ordering, selection markers, or messages.
- Parallel scenario runs must use isolated roots and not share terminal sessions or mutable fixtures.
- Tests must not depend on sleeps or network access.

## Config influence and persistence

Each scenario supplies explicit environment overrides and isolated config/cache roots. Start from a clean environment with only a documented allowlist passed through (e.g. OS-required variables); never read/write the developer's normal IRA config. Persisted state and filesystem outcomes are compared byte-for-byte where the owning feature spec requires compatibility.

## Platform notes

The oracle is a terminal program while the target is a native desktop app. The runner must declare which platforms can execute interactive TUI traces and which can only validate schema/goldens. Linux, macOS, and Windows should share the same scenario contract. Do not claim an OS's live oracle replay if the runner only parses stored captures there. Architecture/platform pre-review must select the PTY/ConPTY strategy, dependencies, and CI installation requirements before red tests are written.

## GPUI/desktop surface

No GPUI dependency in the harness and no UI behavior implementation. A future adapter may translate a scenario into core actions/headless GPUI inputs while the TUI adapter remains frozen and separate. The harness must permit native window smoke evidence to be recorded separately from deterministic core comparisons.

## Write-set and dependencies

Proposed write-set: `tests/parity/**`, a root integration entry `tests/parity.rs` if required, `migration/oracle/scenarios/**`, and a dedicated harness manifest/package only if architecture pre-review chooses one. Shared `Cargo.toml`/`Cargo.lock`, workflow files, and central scripts remain integrator-owned; request those changes before expanding the developer write-set. Preserve all existing captures and the TUI source/tag.

## Test plan

- S1/S6: schema parser contract tests for version, required fields, ordered events, and forward-compatible rejection behavior.
- S2: runner proves it builds/resolves the exact baseline commit (not current HEAD), then launches only that artifact.
- S3: scenario uses unique temp roots; assert screen/process/filesystem/persistence observations are recorded where declared.
- S4: normalization golden tests preserve ordering/messages and replace only declared volatile roots; byte comparison catches persisted-state differences.
- S5: intentionally mismatched expected value reports scenario and observation path; golden mode stages without editing committed fixtures.
- S7: metadata is required and human-review status recorded for each checked-in golden.
- S8: successful tagged baseline trace, malformed scenario, timeout cleanup, parallel fixture isolation and mutation test.

## Open questions for pre-review

1. Should the runner live as a small standalone crate/tool or as root integration tests with a portable PTY dependency? The matrix write-set currently avoids central manifest ownership.
2. What supported runner executes live traces on Windows: ConPTY via a pinned portable PTY library, a maintained native harness, or schema/golden-only validation while live runs remain Linux/macOS?
3. How should the frozen baseline artifact be made reproducible in CI without a slow Cargo build for every test? Prefer a cached baseline build keyed by tag + toolchain + target, with a checksum and a fail-closed missing-artifact path.
4. Which observation adapter contract should F-002 expose so later core tests can compare behavior without coupling to F-003 action names or future GPUI view structs?
