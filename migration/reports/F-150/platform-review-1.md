# Advisory: F-150 by platform-advisor round 1

Scope reviewed: `migration/specs/F-150.md`, `.github/workflows/desktop-build.yml`, root and desktop manifests/lockfiles, F-002 parity-harness branch at `62db2ceba7e7d67b7db60cf280954853d297f9b3`, and the pinned GPUI version. Verdict: **PROCEED WITH CHANGES**. F-150 is feasible on hosted macOS and Windows runners for builds and PTY/ConPTY replay, but its native GUI assertion and live-test invocation need an explicit design before implementation.

## Recommendations (ranked)

1. **R1 [must] Use supported, explicit runner labels and pin/report the Rust toolchain.** Prefer `ubuntu-24.04`, `macos-15` (or an intentional `macos-15-intel` if x86_64 is in scope), and `windows-2022` for predictable MSVC/ConPTY; do not use `windows-latest` for this evidence because its image currently tracks Windows Server 2025. GitHub's current runner image inventory marks macOS 14 deprecated and identifies `macos-15` as arm64 and `macos-15-intel` as x64. Windows Server 2022 meets Microsoft's ConPTY minimum (Server 2019); Windows 10 1809 is the minimum *client*, not the hosted server requirement. Current docs: [GitHub-hosted runner labels/architectures](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [runner image inventory and migration policy](https://github.com/actions/runner-images), [ConPTY minimum supported client/server](https://learn.microsoft.com/en-us/windows/console/createpseudoconsole). In this checkout, `.github/workflows/desktop-build.yml` uses `macos-14` and `windows-latest`; `Cargo.toml` and `desktop/Cargo.toml` are separate manifests with separate v4 lockfiles, and there is no `rust-toolchain.toml`. `dtolnay/rust-toolchain@stable` therefore floats. Pin a stable toolchain (or state the deliberate stable policy and print exact `rustc -Vv`/`cargo -V`); key caches by OS, target, toolchain, and each relevant lock hash.

2. **R2 [must] Make baseline tag availability and live trace invocation explicit.** The baseline resolver builds the exact tagged TUI in a detached worktree (`tools/ira-parity/src/baseline.rs` on the F-002 branch); ordinary `actions/checkout` defaults to shallow history, so CI must fetch the tag/history (`fetch-depth: 0`, or an explicit verified fetch) and log/verify tag SHA before tests. F-002's `f002_contract.rs` currently has macOS/Windows native cases behind both `#[cfg(target_os=...)]` and `#[ignore = "GAP ..."]`; indiscriminately passing `-- --ignored` would run unrelated GAP probes, while ordinary `cargo test` skips the native cases. There is no standalone replay CLI. Add a dedicated live-test target or explicitly select named scenario tests, run it on all three OSes, and fail if zero live scenarios execute. Report exact command(s), scenario IDs/count, baseline SHA, and cleanup outcome. Microsoft's [ConPTY session documentation](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session) confirms this is a native pseudo-console API; the F-002 pinned `portable-pty = 0.9.0` is present in the branch's own lockfile. Important current-state boundary: on `main` at `87d6e5b`, `tools/ira-parity/Cargo.toml` and lockfile do not yet exist; F-002 work is still on a separate branch. F-150 cannot run harness/license steps until that package is integrated.

3. **R3 [must] Keep the license audit anchored to the standalone harness lockfile and include test/dev plus platform-specific dependencies.** Run a pinned `cargo-deny` configuration against `tools/ira-parity/Cargo.toml`/`Cargo.lock`, set `include-dev = true`, allow only reviewed SPDX expressions (with hash-bound clarifications for exceptional crates), and fail on unknown/unreviewed expressions. Also generate and commit a reproducible inventory containing name, version, SPDX expression, and source from locked Cargo metadata; run/check all target-specific dependency closures (or prove the tool resolves all target edges). The branch lock has 61 package entries including target-specific `winapi` crates; auditing root `Cargo.lock` would miss the harness closure. cargo-deny supports a manifest path and license checks, and documents `include-dev`, exceptions and clarifications: [CLI manifest option](https://embarkstudios.github.io/cargo-deny/cli/common.html), [license policy configuration](https://embarkstudios.github.io/cargo-deny/checks/licenses/cfg.html). Pin the cargo-deny version/action too, and record its version and policy digest.

4. **R4 [must] Treat native window smoke as an experiment until the hosted runner proves it.** The current GPUI app (`desktop/src/main.rs`) calls `Application::new()`, opens a window, and activates the app; the current desktop workflow only builds and packages, so it provides no runtime or window evidence. GitHub documents hosted runners as fresh VMs, but the reviewed runner documentation does not promise an interactive GUI session, accessible GPU/display, or reliable UI automation. Therefore the spec's “if hosted runners can launch it reliably” is unresolved, not established. Prototype a bounded smoke that asserts an OS-native window exists (and closes cleanly) on both OSes; process start/exit or successful linking is insufficient. If no stable assertion is available on hosted runners, specify a dedicated interactive self-hosted smoke runner or another automated native-window assertion before calling the clause satisfied. [GitHub hosted runners are VMs](https://docs.github.com/en/actions/how-tos/manage-runners/github-hosted-runners); [self-hosted runners permit controlled hardware/software](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners). Do not mark a compile-only fallback as window smoke.

5. **R5 [should] Spell out locked, all-target test/lint commands and checkout triggers.** Root TUI and desktop are independent Cargo packages, not one workspace, so run each explicitly with `--locked`; do likewise for parity. Use `cargo test --all-targets --locked`, `cargo clippy --all-targets --locked -- -D warnings`, and manifest-scoped `cargo fmt --check` for each package. Run native replay as a separate selected command so filtering cannot silently skip it. Keep desktop binary artifact packaging in `desktop-build.yml`; F-150 itself should have read-only contents permission and no release/upload-release action. The existing `desktop-build.yml` already produces finite-retention test binaries, while `.github/workflows/release.yml` is tag-triggered and has release publishing permissions; neither is a substitute for migration CI.

## Risks and unverified items

- No hosted-runner native-window smoke was executed in this review; window-server/GPU availability and automation reliability on both hosted OSes remain unverified.
- No F-002 build, PTY replay, ConPTY replay, or license tool was run here; the current main branch does not contain the harness. F-002's existing tests show intended macOS and Windows replay entry points but mark them ignored pending CI.
- The proposed `windows-2022` runner's exact current image build can change; record `ImageOS`/`ImageVersion` and `rustc -Vv` per job. GitHub documents Windows Server 2022 as a supported fixed label; Microsoft documents it exceeds the ConPTY server minimum.
- Existing desktop packaging is macOS arm64 on `macos-14`; if x86_64 macOS binary support is an actual product requirement, add a separate Intel runner/target job rather than inferring it from the arm64 job.
