# Blind discovery: filesystem operations and transfers

Date: 2026-10-01
Oracle: `tui-oracle-baseline` = `1cad4ce43cc72d52d4cc4eef920e0da22cb69568`
Scope: file listing metadata, create, go-to-path creation, rename, copy, move, delete, transfer progress/control, and operation-adjacent selection/refresh behavior. This was derived before reading any existing migration inventories, matrix, surfaces, captures, or advisor reports.

## Independently derived behavior checklist

### Listing and metadata

- `list_files` enumerates directory entries and drops names that are not valid UTF-8 (`src/services/list_files.rs:46-66`). It records lossy full paths, label, directory flag, size, and optional mtime (`:1-43`). Metadata follows symlinks; a symlink to a directory is treated as a directory and has size zero, while a failed stat retains the `DirEntry::file_type` hint and gives size 0 / no mtime (`:18-43`).
- The bounded listing path filters dot names when `show_hidden=false`, defaults to 512 entries at its caller, and distinguishes exact-cap complete from overflow using one extra iterator read (`src/services/list_files.rs:68-110`; tests `bounded_listing_reports_complete_for_small_folders`, `bounded_listing_reports_partial_at_the_cap`). Large listing chunks are unsorted, in caller-defined chunk sizes, and read errors print `Error reading entry: {e}` (`:112-146`; `chunked_listing_batches_entries`). Small-list results are label-sorted at `App::list_files_for_pane`; selected state resets to first item or none and selections reset (`src/app.rs:987-1040`).
- Folder-open listing failures are asynchronous and generation-tagged; large folders stream and receive a final sorted pass. The implementation inspected is `App::list_files_for_pane` (`src/app.rs:987-1158`); source comments describe responsiveness, but no runtime timing claim was confirmed here.

### Creating and navigating to paths

- `n` opens a create-name dialog; Enter creates a regular empty file only when the basename contains a non-leading dot and a nonempty suffix, otherwise it creates a directory (`src/handler.rs:242-250` [create dispatch in handler]; `src/app.rs:2793-2923`; helper `path_is_file_kind` near app line 230). Names are trimmed; empty input leaves the dialog active with `Enter a name first.`; existing targets are rejected; nested parent directories are created; file creation uses `create_new` (never truncates); directory creation uses `create_dir_all`. Failures keep the prompt available. A simple result is selected after refresh; nested paths navigate to the created file's parent or deepest folder, and a peer pane on the same parent refreshes (`src/app.rs:2841-2923`). Tests: `new_entry_extension_decides_kind`, `new_entry_selects_created_item_and_works_via_handler`, `new_entry_supports_nested_paths`, `create_never_truncates_existing_sibling`, and `n_dialog_existing_nested_path_errors`.
- `[` opens path input. Existing paths navigate; a path ending in a basename classified as a file opens its parent and selects it. Missing paths create missing parents and then either an empty file via `create_new` or a directory chain, followed by navigation. A create race returning AlreadyExists navigates to the now-existing path instead of replacing it. `~` / `~/...` expand via `dirs_next::home_dir`; relative paths resolve under the active folder (`src/app.rs:2656-2678,2684-2779`, `expand_path` near line 706). Tests: `goto_navigates_to_existing_folder_and_selects_existing_file`, `goto_creates_missing_nested_file_and_folder`, `goto_expands_home_and_relative_paths`, `goto_never_truncates_existing_file`, `goto_never_truncates_on_race`, `n_dialog_expands_tilde`.

### Rename

- Enter starts an inline modal editor prefilled with the full name and caret at the end; arrows move by `char`, Backspace removes before the caret, Escape discards, Enter commits (`src/handler.rs:79-89,345-346`; `src/app.rs:2984-3087`; UI `src/ui/mod.rs:323-331`). Empty/unchanged input closes without filesystem change. Rename is same-directory `std::fs::rename`; a destination whose followed `metadata` succeeds produces `Cannot rename: '<old>' already exists.`; other errors display `Failed to rename: {e}`. It refreshes and clears selection after attempted rename (`src/app.rs:3013-3044`). Tests: `rename_file_in_place`, `rename_cancel_keeps_original_name`, `rename_supports_cursor_and_backspace`.
- Inference/risk from code: because the collision check uses `metadata`, a dangling destination symlink may evade the check; `rename` platform overwrite semantics could therefore differ. This edge has no test found in the inspected operation tests.

### Copy, move, conflict policy, async board

- `c` and `m` request copy/move from the active pane's selected entries, or cursor item when no explicit selection, into the other pane's current folder. No other folder means `The other pane has no folder to copy into.`; any source that is an ancestor of the destination is rejected with `Cannot copy/move a folder into itself.` (`src/handler.rs:286-288`; `App::request_transfer`, `collect_sources`: `src/app.rs:2582-2631,3330-3373`). A y/n confirmation is required; Escape/`n` cancels, Enter/`y` confirms; `o` cycles AutoRename → Overwrite → SkipExisting → AutoRename (`src/handler.rs:172-185`; `src/app.rs:2633-2653`; UI `src/ui/mod.rs:273-320`). Default is AutoRename.
- Each transfer is one worker thread per batch, sequential source paths. Job state/events include start/total bytes, progress/current path, done/cancelled/failed. Total scan becomes indeterminate above 200,000 files or when any source scan is unavailable; copy reads 256 KiB chunks and emits byte progress around each 4 MiB plus per-file completion (`src/services/transfer.rs:164-195,235-331,480-513`). Copy board is shown after confirm but does not take keyboard focus; Tab enters it. On the focused board Up/Down changes job, `p`/Space pauses/resumes, `x` cancels, Escape/backtick closes (`src/app.rs:3411-3446,3449-3514`; `src/handler.rs:209-224`; `src/components/copy_board_ui.rs:14-50`). Completed jobs remain in the board with status labels; active rows show a progress bar and byte count (`copy_board_ui.rs:53-126`).
- Existing destination handling is policy-specific: AutoRename finds first free `stem (2).ext`, `(3)`, etc. (without extension: `name (2)`); Overwrite replaces a non-directory destination file before copying, while directories merge; SkipExisting skips and emits a progress label but counts as a failed item, so the final batch can have Failed status. `create_new` closes the race against clobbering a file (`src/services/transfer.rs:197-233,264-329,420-477`). An overwrite collision with a directory destination recurses into it; same-name child files may fail because recursive copies use `create_new` (not a prompt). Tests: `overwrite_policy_autorenames_collisions`, `overwrite_policy_overwrite_replaces_existing`, `overwrite_policy_skip_existing_keeps_destination`, `policy_cycles_through_dialog_keys`.
- Files copy recursively. Unix copies preserve symlinks themselves (including cyclic links, without dereference), file mode bits, and mtime; directory mode applies after children. Non-Unix (including Windows) follows symlinks by canonicalizing link targets and copies the resolved file/dir; broken/cyclic links error. Copy creates no hard links (`src/services/transfer.rs:333-408,410-478`; tests `copy_preserves_permissions_and_mtime`, `symlinks_are_preserved_not_followed`, `cyclic_symlink_terminates_without_hanging`).
- Move first uses `fs::rename`; only cross-device errors trigger copy then recursive source removal. It does not overwrite an occupied final file; existing destination conflicts become an item failure under policies that do not rename/overwrite. Tests `batch_move_removes_sources`, `move_never_replaces_existing_destination`. Risks to verify on each OS: atomic rename/replacement semantics, move of a directory into an existing directory, Windows symlink fallback, cross-volume partial failure, directory-merge overwrite policy.
- Per-source I/O failure removes the partial destination, preserves that source, continues later batch items, and ends Failed with `N of M items failed`; cancellation is checked before each path and during each file chunk. A cancelled partial item destination is removed, source remains. `remove_tree` uses `symlink_metadata`, so symlinks are removed as links, not traversed (`src/services/transfer.rs:283-329,352-408,515-523`). Tests: `batch_continues_after_io_failure_and_reports_summary`, `cancel_mid_copy_removes_partial_destination`, `batch_cancelled_before_start_copies_nothing`.
- During a live transfer, destination panes refresh about once per second, reveal the first batch path while streaming, preserve an inside-destination cursor, and stop periodic refresh after user navigation. Final completion refreshes both panes and attempts to select the last batch item unless the user moved the cursor. The Copy Board progress persists; no undo history appears in inspected operation paths (`src/app.rs:3428-3446,3620-3746`). Tests: `copied_folder_appears_in_destination_pane_listing`, `moved_folder_appears_in_destination_pane_listing`, `copied_folder_appears_in_large_destination_async_refresh`, `copied_folder_is_revealed_mid_stream_in_large_destination`, `transfer_reveals_folder_live_in_destination_pane`, `navigating_the_destination_pane_during_a_transfer_is_not_yanked_back`.

### Delete

- Delete is permanent recursive removal, not trash. Delete key starts confirmation on selected sources/cursor item. `y`/Enter starts a background path-by-path worker; `n`/Escape cancels before deletion. During work a dismissable dialog says `Deleting done/total — current`; any key hides it but deletion continues. Each top-level path is a cancellation/pause gate; recursive `remove_dir_all` itself is not interruptible. Deletion collects all per-path errors and reports the first plus `(+N more)`; it clears selections and refreshes after a non-cancelled finish (`src/handler.rs:4-14,293-298`; `src/app.rs:3517-3565,3630-3685`; worker `src/services/transfer.rs:525-565`; UI `src/ui/mod.rs:248-271`). Tests: `delete_requires_confirmation_and_removes_on_confirm`, `delete_progress_dialog_is_dismissable`, `delete_keys_depend_on_platform`, `backspace_opens_delete_confirmation_on_macos`.
- Windows/Linux Del triggers delete; macOS Backspace also triggers it; rename-mode Backspace remains text editing. No trash/recycle-bin behavior or undo/redo implementation was found in the inspected file-operation surface.

This is a bounded source/test search, not proof about unclaimed modules; see uncertainty below.

## Risks, ambiguities, and unclaimed edges

1. Source strings and UI event mapping are largely code-derived; no live dialog captures validate exact rendering or focus transitions.
2. Unix-specific symlink preservation differs intentionally from Windows/non-Unix target-follow copy. Windows permission fallback, junctions, and dangling links require real Windows evidence.
3. Cross-device move is copy-then-delete. If source removal fails after copy, destination may remain while source also remains; batch reports an item failure and cleanup logic may remove destination. Exercise this on mounted volumes.
4. Overwrite of merged directories does not recursively replace conflicting children according to a fully documented tree policy; test conflicting nested directory/file shapes.
5. Multi-selection source order comes from the pane's file vector; large streamed results are sorted only in their final pass. Verify deterministic source order under readdir timing.
6. Paths are stored as `String` and labels must be UTF-8 in listing; non-UTF-8 names are omitted, and lossy path conversion can break identity. Windows non-Unicode path parity is especially uncertain.
7. Delete cancellation is only between selected top-level paths; a huge directory deletion may run to completion after user requests cancellation.
8. Listing directory-entry errors are printed to stdout and skipped; invalid UTF-8 labels are silently skipped. No user-facing aggregate listing error was observed.

## Post-derivation comparison with existing artifacts

The independent checklist above was fixed before opening existing artifacts. I compared `migration/inventory/files-ops.md`, `migration/inventory/filesystem.md`, the `files-ops` README/fixture manifest, and captures for listing, create, rename, copy, and move.

Existing operation captures visually show create, rename success/collision, copy/move confirmations and results, including default auto-rename keeping the preexisting destination.
- **Runtime evidence difference:** my PTY session had an empty isolated Home and nonfunctional key injection, so I have no independent live operation observation. Existing `migration/oracle/captures/files-ops/README.md` claims a separate 120x40 PTY run with 12-second startup wait and observed create/rename/copy/move. That external capture evidence corroborates the behaviors but does not change my own runtime status. Its reported delete/progress/pause/cancel/conflict alternatives and recursive/error paths also remain unobserved.
- **Scope/evidence gap:** existing `files-ops` inventory does not cite the transfer-module tests in its transfer rows; my checklist names those tests and therefore adds explicit characterization-test pointers for batch partial failure, overwrite safety, metadata preservation, symlink cycles, and cancellation cleanup. Neither inventory establishes Windows runtime behavior for symlink fallback, cross-device move, or platform rename semantics.
- **Unresolved, not a disagreement:** both inventories notice the source comment's directory-merge promise versus recursive `create_dir`/`create_new` behavior. Neither has a runtime collision fixture for nested directory merge, so preserve this as an open characterization risk.
- **Commit attribution:** `files-ops.md` identifies the correct baseline tag/SHA. `filesystem.md` lists a different commit (`5a990917...`) for its run; confirm those filesystem claims against the frozen tag before treating them as oracle-baseline evidence.

No substantive behavioral contradiction was found between my source-derived checklist and the existing inventory/captures. The reports differ in what each agent personally observed, and both leave destructive/progress and deeper transfer edge cases open.
