# Advisory: platform keymap conflicts by platform-advisor round 1

Scope reviewed: `src/handler.rs`, key descriptions in `docs/features.md`, `src/app.rs` editor/focus behavior, and `desktop/src/main.rs` (which currently has no key bindings). The TUI binding list is a static/code-derived baseline; runtime input behavior still needs oracle captures. Desktop currently has no parity keymap to assess.

Summary verdict: **PROCEED WITH CHANGES**. Keep the TUI bindings as the authoritative action map. Add desktop aliases only where platform conventions conflict, and ensure aliases do not steal text input or replace the original TUI key. macOS system shortcuts and Windows menu activation require explicit conflict policy.

## OS policy

- **macOS:** use Command as native alias modifier where appropriate; preserve literal TUI bindings. Reserve native `Cmd+Q`, `Cmd+W`, `Cmd+H`, and `Cmd+M` for app/window lifecycle only where supported. Avoid stealing Option text composition. Finder's Delete semantics do not change the existing confirmed-delete contract. Apple's [Human Interface Guidelines for keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards/) say to respect standard shortcuts, prefer Command for custom shortcuts, and avoid modifiers that generate characters on localized layouts; implementation and GPUI event mapping remain to be verified against pinned GPUI `0.2.2` source.
- **Windows:** preserve Ctrl-based TUI bindings, but only in file-list/board focus; Windows uses Alt for menu access, and Ctrl+Alt can be AltGr on common layouts. Reserve `Alt+F4` for close/quit. Do not use Win-key bindings. Microsoft explicitly warns against Ctrl+Alt combinations because they may be interpreted as AltGr ([Windows keyboard guidance](https://learn.microsoft.com/en-us/windows/win32/uxguide/inter-keyboard)). Add menu mnemonics without making Alt sequences fire while composing text.
- **Both:** GPUI keymap must not dispatch file operations during IME composition or while text edit, rename, go-to, search, or create dialog owns focus. Current TUI search and dialog code treats `KeyCode::Char` as input; desktop text input must preserve that behavior.
