# Parity matrix

`migration/PARITY_MATRIX.md` is the single ledger of truth. `scripts/parity_gate.py` parses it.
Do not change the column names or order. Rows must start with `| F-`.

## Columns

`| ID | Area | Feature | Surface | TUI refs | Deps | Wave | Status | Owner | Evidence | Gaps |`

- **ID**: `F-001`, `F-002`... stable, never reused. Foundation pieces use `F-0xx` too (area `foundation`).
- **Area**: slice name (navigation, fileops, search, preview, config, input, ...).
- **Feature**: short noun phrase.
- **Surface**: comma-separated `kind:name` items from `surface.txt` that this row covers (for example
  `key:normal:j,key:normal:down,cmd::cd`). The gate requires every `surface.txt` line to appear somewhere here.
- **TUI refs**: `path:line` anchors and the inventory ids (`INV-fileops-004`).
- **Deps**: IDs this row needs first (`F-003,F-010`) or `-`.
- **Wave**: `0` (foundation), `1..n`, or `E` for enrichment-only.
- **Status**: see below.
- **Owner**: current developer agent or branch (`dev:F-017@migrate/F-017-rename`) or `-`.
- **Evidence**: required for VERIFIED. Test names and paths, report paths, commit SHA, CI run ids. Example:
  `tests/rename.rs::{rename_basic,rename_collision}; reports/F-017/adv-2.md; 3fa91c2; ci:macos+windows`
- **Gaps**: open GAP ids, or `-`.

## Status values and transitions

```
NOT_STARTED -> SPECCED -> RED_TESTS -> IN_DEV -> IN_REVIEW -> FIXING -> IN_REVIEW ... -> VERIFIED
                                                                    \-> EQUIVALENT_VERIFIED (terminal-only mapping)
                                                                    \-> WAIVED(D-xxxx)      (exceptional)
BLOCKED(reason)  can be entered from any state, and must be recorded in STATE.md.
REGRESSED        entered from VERIFIED if a later change breaks its tests; re-enters IN_REVIEW.
```

Allowed final states: `VERIFIED`, `EQUIVALENT_VERIFIED`, `WAIVED(D-xxxx)`.

Transition rules:
- `SPECCED` requires `specs/F-xxx.md` with oracle evidence.
- `RED_TESTS` requires failing tests plus GAP notes from the adversarial reviewer committed.
- `IN_REVIEW` requires developer report and a green local build.
- `VERIFIED` requires ALL of: no open `GAP(` or `GAP-FIXED(` referencing this row; logic-reviewer report says
  EQUIVALENT; adversarial-reviewer report says NO FINDINGS (or all resolved); tests run in CI on macOS and Windows;
  Evidence column filled; gate script passes.
- `EQUIVALENT_VERIFIED` requires a decision record with ux-advisor, logic-reviewer, adversarial-reviewer sign-off
  explaining why the terminal-specific behavior maps to the desktop behavior while preserving user intent.
- `WAIVED` requires a decision record with three sign-offs and proof the feature is unreachable or harmful in the
  desktop context (for example, a terminal-escape-sequence quirk). Waivers are rare. Each waiver is listed in
  `FINAL_REPORT.md`.

## Row granularity

One row = one behavior group verifiable by roughly 3 to 15 tests. Split when:
- different keys trigger genuinely different code paths (`d` trash vs `D` permanent delete),
- there are distinct error behaviors,
- modes differ (visual vs normal selection),
- platform behaviors differ.

Merge never; link with Deps instead. If you cannot say how you would verify the row, it is too vague.

## Mandatory coverage rows (add even if the TUI seems not to have them; mark with evidence if absent)

- CLI parity (every flag/subcommand, exit codes, stdout contract)
- Config load, defaults, validation errors, hot reload (if any), first-run behavior
- Every persisted file: read, write, byte-compatible round trip
- Every key binding table, every mode, multi-key sequences, counts/prefixes
- Every dialog and confirmation, with exact texts
- Every error message path
- Startup and shutdown (session restore, unsaved state, exit codes, stdout on exit)
- Help screen contents
- Resize and small-window behavior (translated to window min sizes and responsive layout)
- Performance baselines

## Maintenance protocol

- Only the manager edits the matrix. Developers and reviewers propose through reports.
- After each loop update statuses from facts: re-run gate; reconcile with GAP notes in the tree.
- Keep a count summary at the top of `STATE.md` (generated by `python scripts/parity_gate.py --summary`).
- A new TUI behavior found later is a new row at once. Never edit history: add `F-0nn` and note origin.
- Regression handling: set `REGRESSED`, add the cause to `journal.md`.

## Audit questions (ask before trusting the matrix)

1. Does every `surface.txt` line map to a row? (script checks)
2. Does every inventory `INV-` entry appear in some row's TUI refs? (`grep` each id)
3. Does every TUI source file appear in some row's refs or an inventory orphan note?
4. Does every row have an owner or wave assignment?
5. Is any row VERIFIED whose Evidence column is vague ("tested")? Reject; require names and paths.
